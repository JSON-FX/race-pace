Loading states — three directions

Why the five new pages feel dead on click, and three ways to fix it. All are reduced-motion safe.

The cause is not slowness — it's silence. Four routes already ship a loading.tsx (payments, registrations, events, team). App Router renders that file the INSTANT a navigation starts, so those pages feel responsive. The five pages added in this branch — dashboard, check-in, organizations, commission, payouts — have none, so the browser sits on the old screen with no acknowledgement until the server replies. Same server, same latency; the difference is entirely feedback.

Smallest change, and already the house style. One loading.tsx per new route, shaped like that page's real layout — four KPI tiles for the dashboard, two tables for check-in, and so on. Downside: it only covers the main pane, so the click itself still has no immediate acknowledgement in the sidebar.

Recommended. The two solve different halves. The bar answers "did my click register?" in under 100ms — the question the operator is actually asking. The skeleton answers "what am I getting?" and reserves the layout so nothing jumps. Together they cover both the navigation and the render, and the bar keeps working on routes that never get a bespoke skeleton.
Rejected · Centred spinner
Race Pace
Dashboard

Why not. A spinner blanks the whole pane, so the layout jumps when content lands, and it conveys nothing about what is coming — a one-row table and a full dashboard look identical while loading. It also reads as slower than a skeleton of the same duration, which is the opposite of the goal here.
Accessibility, applies to all three. The bar and skeletons must respect prefers-reduced-motion — pulsing and sliding become a static tinted block, still visible, just not animated. The progress bar needs role="progressbar" with an accessible name, and the loading region an aria-busy, so a screen-reader user is told the page is working rather than being left on a silent screen.
