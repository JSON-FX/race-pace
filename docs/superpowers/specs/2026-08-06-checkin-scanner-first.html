Check-in — scanner-first, with roster

Revised from Direction B. A hardware 2D imager is the primary input; the camera and the roster are fallbacks that are always present rather than modes you switch into. The two tables you asked for sit below the scan bar, both searchable and filterable by category.

PRIMARY
USB / Bluetooth 2D imager
Acts as a keyboard — types the 188-char token and presses Enter into a permanently focused field. No driver, no decode library, no camera permission.
FALLBACK
Device camera
Phone rear camera, laptop or USB webcam. Needs jsQR + a camera grant. Fixed-focus webcams struggle at 10–20 cm against screen glare.
ALWAYS AVAILABLE
Manual tap in roster
Dead phone, cracked screen, runner who never opened the app. One tap on the row checks them in — the only path that works with no hardware at all.

One roster query feeds both tables. checkin_roster(event_id) already returns runner, bib, category, status and checked_in_at for every paid or pending entry — the two tables are just that one result split on whether checked_in_at is null. Search and the category chips filter client-side over rows already in memory, so they stay instant with no round trip.
Two rules worth confirming. An unpaid entry shows as Blocked rather than checkable — the existing Edge Function already returns not_paid (409) and refuses it, so the row reflects a rule the server enforces rather than inventing a new one. And a re-scan of someone already in returns already: true, which surfaces as an amber "already checked in at 08:14" instead of a green tick, so a double-scan never reads as a fresh success.
